still require owner verification; path lookup is not that verification.

Product original; the adapter does not create an attempt or split its charge.

selection, duplicate JSON or closure identities, incorrect raw-byte pins,
overlapping roots and paths that could inject environment or PATH entries.

allocation, subprocess start, signing, scheduling or resource enforcement.
The tests use synthetic metadata; they are not native toolchain proof.

without executing those files. On ENG-UK the original proposal fails both the

## Existing Darwin boundary that must be retained

The Product driver checks the `node` closure role against
`realpath(process.execPath)`. `seatterm`'s Darwin `checkExpectedSHA256` hashes
and runs a private executable copy; it also explicitly refuses a declared
install-path requirement combined with that pinning mechanism. Relocating Node
therefore changes the identity checked by this Product driver.

The returned DATA is deliberately **not** `seatterm.Command`. Its stable
executable-path requirement is not a bypass flag. This patch does not change
`seatterm`, clear an expected pin, or silently substitute an unpinned session
command. Pomar must accept or amend the invocation mapping at its actual
Darwin launcher, including how the owner stages and pins the final executable
path without another relocation. Existing provider-fence source preparation
does not supply a connected native launcher or a launch/admission receipt.
